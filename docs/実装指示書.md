## 5. 実装タスク（T0〜T14）

### T0：技術スパイク【9/4・最優先・同日中に完了させる】

`spikes/` 配下。捨てコードでよい。**本体から参照しない。**

| ID | 内容 | 受入条件 | × のときの迂回 |
|---|---|---|---|
| **S-1** | .NET 10 上で fo-dicom 5.2.6 の最小 SCP を立て、`echoscu` / `findscu` から応答を得る | 両方 Success | `Directory.Build.props` の TFM を `net8.0` に変更。CLAUDE.md も書き換える。**本番リリース前に .NET 10 へ移行する TODO を docs に残す** |
| **S-2** | `ISO_IR 192` と `ISO 2022 IR 13\ISO 2022 IR 87` の両方で PN を encode → ファイル出力 → `dcmdump` で decode。漢字・カナ・外字（髙・﨑・德）・長音・濁点・30文字級を含める | 往復一致し、16進で符号（ISO 2022 なら `1B 24 42` 等）が正しい | T7 で PN を自前 `byte[]` 生成する実装に切り替える。**2〜3日を見込み、他機能を削って確保** |

**⚠ `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` の呼び忘れを S-2 で同時に潰すこと。**

**⚠ S-2 の合否は16進バイト列で判定する。**この端末のコンソールは CP932（Shift-JIS）のため、`dcmdump` の画面表示で判断すると誤判定する。`Format-Hex` または `dcmdump +U8` を使う。

### T1：ソリューション骨格＋設定読込＋バリデータ【9/7】

- §1 の構成でプロジェクトを作成。`Directory.Build.props` と `Directory.Packages.props` で一元管理。
- JSONC ローダ（`JsonCommentHandling.Skip`）、`_base.jsonc` との深いマージ、`DeviceProfile` モデル。
- バリデータ：JSON構文 → `schemaVersion` → タグ形式 `(gggg,eeee)` → **DICOM 辞書との VR 一致** → VM → SQ 入れ子（2階層以内）→ `db:` の列が実在 → `specificCharacterSet` が既知の定義語 → 禁止式（任意コード実行）の検出。
- `mwm-admin validate --profile <id>`。

**受入条件**：正常なプロファイルが読める／わざと壊した5パターン（括弧欠落・未知タグ・VR誤り・存在しない列・不正 charset）すべてで**エラー位置つきで検証失敗**する。

---

### T2：SQLite ストア＋UID 採番【9/7〜9/8】

- 開発計画 v2 付録A の DDL をそのまま実装。マイグレーションは単純な冪等 DDL でよい。
- `IWorklistWriter.UpsertAsync`：**1トランザクション**で `Patient` upsert → `WorkItem` upsert → `UidAllocation` で StudyInstanceUID を採番。
- `IUidAllocator`：`2.25.` + `Guid.NewGuid()` の128ビットを整数として10進表記（先頭ゼロ除去）。
- `IWorklistRepository.QueryAsync`：粗い SQL 絞り込み（日付・DeviceProfileId・Status・Station AE）。
- WAL / `busy_timeout=5000` / SCP 側は `Mode=ReadOnly`。

**受入条件**
- 同じ `WorklistUpsertRequest` を100回 upsert しても行が増えず、**StudyInstanceUID が変わらない**。
- 10スレッド同時 upsert ＋ 10スレッド同時 query でロック例外なし（E-13）。
- upsert の途中（トランザクション中）に query しても中途半端な行が見えない（E-14）。
- 生成した UID が `^2\.25\.\d{1,39}$` にマッチし、100万回生成して重複ゼロ。

---

### T3：C-ECHO SCP ＋ アソシエーション制御【9/8〜9/9】

- `DicomService` 派生。`IDicomServiceProvider` / `IDicomCEchoProvider`。
- `OnReceiveAssociationRequestAsync`：ルーティングでプロファイル解決 → **解決したルールをログに出す** → AE 照合（`strict`/`logOnly`/`ignore`）→ PC ごとに accept / reject。
- Windows サービス化（`UseWindowsService`）、`--console` で開発起動。

**受入条件**：N-17 / N-18 / E-07 / E-08 / E-09 が通る。`strict` での拒否は**理由コード付き A-ASSOCIATE-RJ**（黙って切らない）。

---

### T4：C-FIND 最小（固定1件）【9/9】

- `IDicomCFindProvider.OnCFindRequestAsync` を `IAsyncEnumerable<DicomCFindResponse>` で実装。
- ハードコードした1件を Pending で返し、最後に Success。

**受入条件**：`findscu -W` で1件返り、`dcmdump` で SQ 構造が読める（N-16）。**ここで一度 pcap を取り、以後の「正解サンプル」にする。**

---

### T5：MatchEngine【9/10〜9/11】

- Range Matching（`YYYYMMDD-YYYYMMDD`、片側開放）／Wildcard（`*` `?`）／Universal（空値）。
- **日付クランプ**：装置の要求範囲 ∩ プロファイルの有効窓。クランプの有無を `ClampResult` で返す。
- **決定論的 sort**：`active desc, ScheduledTime asc, StablePatientId asc`。
- `maxResults` で打ち切り、`Success` で終える。
- `modalityMatching`：`strict` / `lenient` / `ignore`。

**受入条件**：N-02〜N-13、E-05、E-06 が通る。**特に N-06（装置既定の広範囲でクランプが働き当日分のみ返る）は必須。**

---

### T6：DatasetBuilder【9/11〜9/14】

- `source` DSL：`db:` / `const:` / `echo:` / `uid:study` / `coalesce:[...]` / `auto:*`。
- `fallback` / `required` / `onMissing`（`empty`/`omit`/`reject-item`）/ `maxLength` / `when`。
- SQ の入れ子生成。`echo:` は SQ 内も探索する。
- **来歴（Provenance）を同時に返す**：`{"(0010,0020)": "db:StablePatientId", ...}`。
- **1件の生成失敗で全体を落とさない。**その行を `Suppressed` にして続行。

**受入条件**：付録B のプロファイルから期待どおりのデータセットが生成される／`required` 欠損で `Suppressed` になり監査に残る（E-11）／`echo:` が SQ 内のタグを拾える。

---

### T7：PnEncoder（文字コード4案）【9/14〜9/15】

- `charset.patientName` の群割当（`none`/`kanaHalf`/`kanaFull`/`romaji`）に従って PN を組む。
- **`SpecificCharacterSet` を最初に設定する。**
- 全角カナ→半角カナ変換は**自前の変換表**を持つ（外字・長音・「ヴ」・濁点の分解を明示できる）。
- **encode → decode の往復検証**を行い、代替文字が出たら `false` を返す。
- 4案分のプロファイルを `config/profiles/` に用意する。

**受入条件**：N-14 / N-15 / E-12 が通る。**4案すべてで `mwm-scu preview` が期待バイト列を出す**（16進で目視確認できる）。

---

### T8：監査＋explain-query【9/15】

- `AuditCFind`：要求データセットを **DICOM JSON Model** で `RequestJson` に保存（**後日の再生に使う最重要データ**）。criteria / clamped / explain / 件数 / 所要時間 / status / `PeerAborted`。
- `AuditCFindItem`：来歴と suppressed 理由。
- `mwm-admin explain-query --run <id>`：**各条件で候補が何件落ちたか**を表示。

**受入条件**：0件になるクエリに対し、`explain-query` が「日付で N件→M件、Station AE で M件→0件」のように**どこで落ちたかを特定できる**。

---

### T9：raw stream recorder【9/16】

- T0/S-3 の結果に従って ①→②→③ の順に実装。
- 形式：固定ヘッダ（UTC ticks / 方向 / association ID / chunk length）＋ raw bytes の**追記専用バイナリ**、別に index JSONL。
- **bounded channel** で書き込み。満杯時も DICOM 処理を止めず、**欠落を件数で記録しアラーム**にする。
- 日次／容量ローテーション、SHA-256。

**受入条件**：C-ECHO 1往復と C-FIND 1往復の全バイトがファイルから復元でき、pcap と突き合わせて一致する。

---

### T10：ホットリロード＋自動ロールバック【9/16】

- `FileSystemWatcher` ＋ 500ms デバウンス → 検証 → **成功時のみ差し替え**。
- **失敗時は稼働中の設定を維持**し、ログと `00_watch` にエラーを出す。
- 成功時に `config/backup/<id>.<timestamp>.jsonc` へ自動バックアップ（**当日の変更履歴が証跡になる**）。
- **進行中のアソシエーションは読込時のスナップショットを使い続ける。**
- 旧→新の差分をログに出す。
- 起動時は検証失敗＝起動失敗（イベントログに理由）。

**受入条件**：L-03（設定破壊テスト）が通る。稼働中に文字コードプロファイルを差し替え、**次のアソシエーションから新設定が効く**。

### T11：mwm-scu / mwm-admin CLI【9/16〜9/17】

`Ascube.Mwm.Tools` を self-contained 単一 exe で発行。

| コマンド | 内容 |
|---|---|
| `scu echo` | C-ECHO |
| `scu find` | C-FIND（全マッチングキー＋Detailed Query 相当4項目を指定可） |
| `scu find --emulate-apex-defaults` | Days Back 60 / Forward 2 / Max Hits 60 を再現 |
| `scu find --hard-close-after N --close-mode fin\|rst` | **★N件受信後に A-RELEASE を送らず TCP を閉じる** |
| `scu replay --from-audit <id>` | `AuditCFind.RequestJson` から装置の実クエリを復元して再送 |
| `scu preview --profile <id> --patient <id>` | **装置なしで**生成データセットを `dcmdump` 形式＋16進で表示 |
| `admin validate --profile <id>` | 設定検証のみ |
| `admin health` | 待受状態／直近アソシエーション／プロファイル／リロード成否 |
| `admin explain-query --run <id>` | 0件の原因特定 |
| `admin export-support-bundle` | 証跡パッケージ生成 |

⚠ **`--hard-close-after` は `DicomClient` では実現できない**（内部で A-RELEASE を送りうる）。`TcpClient` で自前接続し、PDU を数えながら読み、N件目で `socket.LingerState = new LingerOption(true, 0); socket.Close();`（RST）または `Shutdown` → `Close`（FIN）を行う経路を別に持つこと。**FIN と RST の両方を用意する。**

**受入条件**：R-SCU-01〜07 すべて。E-02 / E-03 が `--close-mode fin` / `rst` の両方で SCP を壊さないことを確認できる。

## 6. やってはいけないこと（禁止事項）

| # | 禁止 | 理由 |
|---|---|---|
| 1 | C-FIND のたびに StudyInstanceUID を採番する | PACS で1検査が複数スタディに分裂。運用開始後に発覚 |
| 2 | 0件で Error / `QueryRetrieveUnableToProcess` を返す | 装置画面にエラーが出る |
| 3 | `OnConnectionClosed` で例外を再スローする | リスナが道連れになり「二度と繋がらない」 |
| 4 | 患者項目をダミー値で補完する | ダミーの患者情報が画像に焼き付く |
| 5 | SCP から SQLite に書き込む | 連携の一方向性が壊れ、障害解析ができなくなる |
| 6 | SQLite をネットワーク共有に置く | ロックが正しく動作せず破損する |
| 7 | `AccessionNumber` を `WorkItem` の主キーにする | 年度で重複しうる／未採番の検査を保持できない |
| 8 | `SpecificCharacterSet` を後から設定する／`ISO 2022 IR 87` を単独値にする | 符号化が壊れる。当日最も時間を溶かす形で現れる |
| 9 | 検証に失敗した設定を適用する | 現場の1文字のミスが検査停止に直結 |
| 10 | fo-dicom を fork・改変する | 保守不能になる。拡張点で足りなければ透過 proxy を使う |
| 11 | GPL コードを取り込む／Npcap を同梱する | ライセンス違反 |
| 12 | tool 出力から読んだ内容を再入力してファイルを書き直す | 切り捨てられている可能性がある |
| 13 | 自作 SCU だけで「規格として正しい」と判定する | 同じ fo-dicom なので同じバグを再現する |
| 14 | `wlmscpfs` とバイナリ完全一致を期待する | 正常でも異なる。意味比較で行う |
| 15 | GUI を作る | 11営業日では他の必須項目を押し出す |
