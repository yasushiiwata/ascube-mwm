## 1. まず知っておくこと：当日のコマンドは `C:\dev\site` を使う

**`C:\dev\ascube-mwm\scripts\` を直接叩かないでください。** サービスとして登録した SCP は、
リポジトリとは**別の場所**のDBを使います。

| | リポジトリのスクリプト既定値 | サービスが実際に使う場所 |
|---|---|---|
| ワークリストDB | `C:\dev\ascube-mwm\data\mwm.db` | **`C:\Ascube\MwmData\mwm.db`** |
| 監査DB | `...\data\mwm-audit.db` | **`C:\Ascube\MwmData\mwm-audit.db`** |
| プロファイル | `...\config\profiles` | **`C:\Ascube\Mwm\config\profiles`** |

`01_health.ps1` / `05_explain.ps1` / `07_set-current.ps1` / `08_clear-current.ps1` は
既定値が `..\data\` を向いたままです。サービス登録後にそのまま叩くと——

> **別のDBを読んで、黙って嘘の答えを返します。エラーは出ません。**

`01_health.ps1` は「受診者なし」と言い、`05_explain.ps1` は存在しない RunId を探し、
`07_set-current.ps1` は誰も読まないDBに書き込みます。

`05_explain.ps1` はスクリプト自身が「9/28に『0件です』で止まらないための最重要コマンド」と
名乗っているものです。**それが別の監査DBを読むのは致命的です。**

### 対策

`C:\dev\site\` に、正しいパスを固定したラッパーを置いてあります。**当日はこのフォルダだけを使います。**

| コマンド | 用途 |
|---|---|
| `.\watch.ps1` | **朝いちばんに起動して一日出しっぱなしにする監視画面** |
| `.\health.ps1` | 単発の状態確認 |
| `.\find.ps1` | C-FIND を撃つ（`-PatientId <12桁>` で指名も可） |
| `.\explain.ps1 -RunId <id>` | **「0件です」の原因を名指しする。当日いちばん使う** |
| `.\set-current.ps1` / `.\clear-current.ps1` | 受診者のセット／クリア |

C-ECHO（`scripts\03_echo.ps1`）はDBを読まないのでそのままで構いません。
文字コード切替（`switch-charset.ps1`）もそのままですが、**プロファイル置き場が
`C:\Ascube\Mwm\config\profiles` である**点に注意してください。

## 2. FIX-001：実機で見つかった欠陥（修正済み）

### 何だったか

`mwm.db` が存在しない状態で C-FIND を受けると、例外が投げられてアソシエーションが切れていました。
SCU 側には `The connection closed prematurely` と見えます。**C-ECHO は成功します。**

規則2「0件は Success」に違反していました。

### なぜ 9/28 に直撃するところだったか

**当日の朝、最も普通に起こる状態がこれでした。**

1. サービスが自動起動する
2. まだ誰も受診していない → BRIDGE-Navi は `SetCurrentAsync` を一度も呼んでいない
3. `mwm.db` はまだ存在しない
4. メーカーエンジニアが装置から疎通確認の C-FIND を撃つ
5. **装置にはエラーとして見える**

当日いちばん最初の操作が、いちばん最初の地雷でした。
しかも echo は通るので、「echo は通るのに find だけ落ちる」という原因を見失いやすい形で出ます。

232件のテストが green だったのにこれが残っていたのは、**テストが常にDBを用意してから叩いていたため**です。
実機に素の状態で置いて初めて出ました。

### 直した内容

`SqliteWorklistRepository` の4つの入口で、`OpenAsync` の前に `File.Exists` を確認し、
DB未作成時は「受診者なし」を返します。テスト5本追加、237件 green。

判定しているのは**ファイルが無いことだけ**です。権限エラーやファイル破損は従来どおり例外として上に投げます。
握りつぶすと、DBが壊れていても「0件です」としか言わなくなり、1人モデルで最悪の事故に近づくためです。

### ここから引き出すべき教訓

**素の状態から叩く確認は、実機でしか意味がありません。** 自動テストは「用意された状態」しか試しません。
9/24 の設置後も、DBを消した状態で一度 echo → find を通してください。

## 5. 時刻同期

**設置時、この機体は一度も時刻同期していませんでした**（`ソース: Local CMOS Clock`）。
現在は `ntp.nict.jp` と同期し、ずれはミリ秒単位です。

`ScheduledProcedureStepStartDate` が今日かどうかで応答が決まる作りなので、
**日付が1日ずれれば当日いきなり 0件**になります。しかも `explain` は
「ScheduledDate が要求範囲外」と正しく報告するだけなので、原因が時計だと気づくまで時間を溶かします。

**9/24 の設置時と 9/28 の朝、必ず確認してください。**

```powershell
w32tm /query /status
```

`閏インジケーター: 0` なら同期できています。`3` なら同期できていません。

## 7. 当日 0件になったときの手順

**当てずっぽうで直さないこと。** 原因を名指しする機能が入っています。

```powershell
cd C:\dev\site
.\health.ps1              # RunId を確認
.\explain.ps1 -RunId <id>
```

次の6つのどれかを、値つきで教えてくれます。

1. `CurrentEntry` が無い（誰も設定されていない）
2. TTL 切れ
3. `ScheduledDate` が要求範囲外（→ **時計を疑う**）
4. PatientID / PatientName の指名が一致しない
5. `DatasetBuilder` が `Suppressed`
6. **ワークリストDBが未作成**（FIX-001 で追加。正常系）

**そして繰り返しますが、0件は正常応答です。**
該当者が特定できないときは 0件＋Success を返します。1人モデルで「とりあえず今日の一覧を返す」と、
**他人を返す**ことになるためです。「0件だから壊れている」と読まないでください。
