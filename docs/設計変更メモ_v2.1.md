### A-2. §4-3 患者氏名の文字コード — **4案から3案へ（案③を作らない）**

**案③を作らない根拠**

1. **技術的に、ライブラリのままでは出せない。**S-2 で確認したとおり fo-dicom はエスケープシーケンスを出力しない。自前 `byte[]` エンコーダが必要で、**いま作るなら 2〜3日**（9/28 の pcap で装置の実挙動が分かった後なら 1〜2日）。残り10営業日の 20〜30% を占める。

   ⚠ 参考：`ISO 2022 IR 13\ISO 2022 IR 87` で本来現れるべきエスケープは、**漢字への切替 `1B 24 42`（ESC $ B）／復帰 `1B 28 4A`（ESC ( J ＝ JIS X 0201 Roman）**。`1B 28 42`（ESC ( B ＝ ASCII）は `ISO 2022 IR 6\ISO 2022 IR 87` の組合せの値です。開発計画 v2 §6-2 と `docs/TODO.md` は後者の値を書いているので、**組合せによって違う**ことを注記しておきます。
2. **必要になる条件が狭い。**案③が要るのは「**装置が UTF-8 を拒否し、かつ漢字が必須**」の場合だけ。APEX 5.6 の適合性宣言は `ISO_IR 192` と `ISO_IR 13` の**両方を宣言**しており、**装置自身が UTF-8 を生成する**（§1-3 参照）。この2条件が同時に成立する確率は低い。
3. **代替がある。**漢字が出せなくても、④（半角カナ単独）で受診者の同定はできる。**検査は止まらない。**
4. **後から作れる。**万一 9/28 に UTF-8 が通らなかった場合、pcap に装置の実挙動が残る。それを見てから作るほうが、当てずっぽうで作るより速く確実。

⚠ **これは「やらない」ことの記録です。**後日「なぜ ISO 2022 に対応していないのか」と問われたときのために、`docs/TODO.md` に**自前 PN エンコーダ（見積 1〜2日、着手条件：9/28 で UTF-8 が通らなかった場合）**として明記します。

⚠ **§4-3 の注意書き「`ISO 2022 IR 87` を単独値で設定してはならない」は規格の話として引き続き正しい**が、そもそも ISO 2022 系を使わないため実務では発生しない。代わりに**プロファイル検証で `ISO 2022` を含む値を検証失敗にする**（現場で誤って書けないようにする）。

### A-3. 案④は未検証 — 実装前に1時間で確認する

`ISO_IR 13` を**単独値**で使うのは単一バイト集合なので原理的には問題ないが、**fo-dicom で実際に JIS X 0201 の 0xA1〜0xDF が出るかは未確認**です。T7 の着手前に `spikes/S2_charset_roundtrip` に追加してください。

## B. 1人モデル（最も大きな変更）

### B-1. 判明した事実

> MWM サーバは、BRIDGE-Navi の端末（PC もしくは Windows タブレット）になります。つまり、MWM サーバは**1対1対応**となります。
> したがって、健診者情報は、**その日1日のみ、で、かつ、1人だけです（常に）。**

BRIDGE-Navi は健診ブースごとに端末が置かれる構成で、骨密度ブースの端末が MWM サーバを兼ねます。装置とブース端末が1対1なので、**ワークリストに載るのは常に「今このブースにいる1人」だけ**です。

### B-2. §4-7（画面表示中の健診者との連動）— **全面差し替え**

開発計画 v2 §4-7 は次のように書いていました。

> ⚠ **「選択中の1名だけを返す」モードは既定にしない。**（中略）**フォーカス未設定時は当日全件にフォールバックする。**

**→ この判断を撤回します。**多数の受診者が同じワークリストに並ぶ構成を想定した判断でした。1人モデルでは、フォールバックで返るのは**別人**です。

| | 開発計画 v2 | **本メモ** |
|---|---|---|
| 既定モード | `visibility: active-preferred` | **「現在の1人」のみ。他に選択肢を作らない** |
| フォーカス未設定時 | 当日全件にフォールバック | **0件＋Success を返す** |
| `fallbackToAllTodayWhenNoActive`（付録B） | `true` | **撤回。設定項目ごと削除する** |

**新しい安全側の原則**

> **該当者が特定できないときは0件を返す。古い1人を返さない。**

⚠ 「0件が返ると技師には壊れているように見える」という §4-7 の懸念は残ります。**しかし1人モデルでは、間違った1人を返すほうがはるかに悪い。**0件は `admin health` と `00_watch.ps1` の「現在の受診者：なし」で即座に説明できます（実装指示書 v2 §5-T8 / T12）。

### B-3. 前の受診者を消し忘れる事故への対策（三重）

このモデルで最悪の事故は、**前の受診者を消し忘れて次の人の検査に載せること**です。三重に防ぎます。

| 層 | 内容 |
|---|---|
| 1 | **`SetCurrentAsync` は常に置き換え。**追加ではないので、次の人を設定した時点で前の人は消える |
| 2 | **`CurrentTtl`（既定15分）で自動失効。**`ClearCurrentAsync` を呼び忘れても、TTL 経過後は0件になる |
| 3 | **`00_watch.ps1` に「現在の受診者：あり／なし、TTL 残 mm:ss」を表示。**当日、画面を見て真っ先に確認する項目 |

⚠ TTL は保険であって設計の代わりではありません。BRIDGE-Navi 側の画面遷移の分岐（中断・スキップ・強制終了）すべてから `ClearCurrentAsync` を通してください。

### B-4. §4-2（日付クランプ）— 重要度が下がる。ただし残す

開発計画 v2 は日付クランプを「本設計の中核」と位置づけていました。根拠は **Days Back 60 / Max Hits 60 の組合せで、返る60件が古い60件になり、今日の受診者が永遠に出てこない**という予測でした。

**1人モデルでは候補が最大1件なので、この問題は起きません。**

ただし**クランプ自体は残します。**装置が「今日」以外の範囲を要求したときに、`CurrentEntry` を誤って返さないためです。実装は「要求範囲に `ScheduledDate` が入るかどうか」の判定に簡素化されます（実装指示書 v2 §5-T5）。

### B-5. 付録A（SQLite スキーマ）— `ActiveContext` を `CurrentEntry` に置換

```sql
-- 廃止：ActiveContext（装置プロファイルごとに「選択中の受診者」を持つ設計）
-- 新設：CurrentEntry（この端末に「今」載っている受診者。常に0行か1行）
CREATE TABLE CurrentEntry (
  Singleton       INTEGER PRIMARY KEY CHECK (Singleton = 1),   -- ★常に1行に強制
  WorkItemId      TEXT NOT NULL,
  DeviceProfileId TEXT NOT NULL,
  SetAtUtc        TEXT NOT NULL,
  ExpiresAtUtc    TEXT NOT NULL
);
```

`Patient` / `WorkItem` / `UidAllocation` / `AuditCFind` / `AuditCFindItem` は**付録A のまま変更なし**。`WorkItem` は履歴として残します（監査、および同じ人が同日に再測定するときの UID 再利用のため）。

### B-6. 付録B（プロファイル）— `visibility` ブロックの変更

```jsonc
// 開発計画 v2 付録B
"visibility": {
  "mode": "active-preferred",
  "activeTtlMinutes": 15,
  "fallbackToAllTodayWhenNoActive": true    // ← ★削除する
}

// 本メモ
"visibility": {
  "mode": "current-only",     // 固定。他の値を許可しない
  "currentTtlMinutes": 15
}
```

あわせて `matching.maxResults`（v2 は 50）は**1で固定**、`matching.responseOrder`（決定論的 sort）は**不要**になります。

### B-7. `IWorklistWriter` の形が変わる（BRIDGE-Navi への影響）

大徳君に渡した仕様が正です。開発計画 v2 §5（BRIDGE-Navi 連携）の `UpsertAsync` / `SetActiveAsync` / `ClearActiveAsync` は**廃止**。

```csharp
public interface IWorklistWriter
{
    Task SetCurrentAsync(WorklistEntry entry, CancellationToken ct = default);
    Task ClearCurrentAsync(CancellationToken ct = default);
    Task<WorklistEntry?> GetCurrentAsync(CancellationToken ct = default);
}
```

`WorklistEntry` は**名前付きプロパティの record**にします（位置引数にしない）。理由：`StablePatientId` と `AccessionNumber`、`FamilyNameKana` と `FamilyNameKanji` のように、**取り違えても型エラーにならない**組合せが多すぎるためです。詳細は実装指示書 v2 §3。

### C-3. §4-6（値を捏造しない）に追加

> **前回・前々回の身長体重を当日値として送らない。**未測定ならタグごと省略する（`onMissing: omit`）。

⚠ **ブースの巡回順は誘導アルゴリズムが決めるため、骨密度が身長体重より先になる場合があります。**「未測定なら省略」は例外経路ではなく、**通常起こる経路**です。

### C-3-2. 性別の未定義値は `O` にしない

項番8 は `1`:男性 / `2`:女性 です。**それ以外（空欄・想定外の値）に `O`（その他）を入れてはいけません。**`O` は「その他」という**実在の値の主張**であり、§4-6 の値の捏造にあたります。

**`(0010,0040)` PatientSex は空値で返します。**MWM の PatientSex は Type 2 なので、長さ0で返すことが規格上正しい扱いです。`enum Sex` の `Unknown` をこの用途に使います。

### C-4. 患者氏名の元データ（§4-3 の前提）

| 項番 | 内容 | 文字種 | 区切り |
|---:|---|---|---|
| 6 | カナ氏名 | **半角カナ** | 半角スペース（0x20） |
| 7 | 漢字氏名 | 全角 | 全角スペース（U+3000） |

⚠ **カナは半角で来ます。**案①（PN 第1群＝全角カナ）は変換を1回挟みます。`ﾀﾞ` は「`ﾀ` + `ﾞ`」の2文字で来るため、全角化では `ダ` の1文字に**結合**が必要です（半濁点も同様）。自前の変換表で明示的に扱います（実装指示書 v2 §5-T7）。

⚠ **BRIDGE-Navi は半角のまま渡します。**全角化するかどうかは文字コード案（①②④）で変わるため、SCP 側で決めます。BRIDGE-Navi 側で変換すると、当日プロファイルを切り替えても直りません。

⚠ **姓名の区切りが無い／2つ以上ある場合**：区切りが無ければ全体を姓に入れて名は空、3つ以上なら最初を姓・残りを結合して名。**いずれも監査ログに残す。**

```markdown
18. 依頼電文の項番3（個人番号・12桁）と項番4（受診番号・5桁）を取り違えない。
    PatientID に入れるのは項番3。
```
